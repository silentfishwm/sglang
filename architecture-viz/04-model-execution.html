Phase II · The Core Engine

04 · Model Execution: ModelRunner, Attention Backends & CUDA Graphs

The scheduler (chapter 02) decides what to run; this chapter is about how it runs. ModelRunner owns the model weights, the KV-cache pools, the attention backends, and the CUDA graph runners — and turns a ForwardBatch into logits and sampled tokens, thousands of times per second.

4.1ModelRunner's place in the stack

Recall from chapter 01: each scheduler subprocess embeds a TpModelWorker, which embeds a ModelRunner (python/sglang/srt/model_executor/model_runner.py, ~1900 lines). The call chain per iteration is Scheduler.run_batch → TpModelWorker.forward_batch_generation → ModelRunner.forward → model.forward(...) — the last hop lands in an ordinary nn.Module like LlamaForCausalLM.

Construction is deliberately staged. ModelRunner.__init__ gets you a loaded model and a distributed world — but no memory pools and no CUDA graphs. The owner (TpModelWorker, python/sglang/srt/managers/tp_worker.py:365-404) calls three more methods in a fixed order, because each stage needs the previous one: backends need pools to index into, graphs need backends to capture.

4.2ForwardBatch: the GPU-side view of a batch

The scheduler's ScheduleBatch is high-level, mostly-CPU bookkeeping. Right before the forward pass it is lowered into a ForwardBatch (python/sglang/srt/model_executor/forward_batch_info.py:412) — "low-level tensor data, mostly GPU tensors", built by ForwardBatch.init_new. Every attention backend, CUDA graph runner, and model forward reads from this one dataclass.

    self, forward_batch: ForwardBatch, pp_proxy_tensors=None, **kwargs

    mode = forward_batch.forward_mode
    if mode.is_decode():
        return self._execute_decode(forward_batch, pp_proxy_tensors)
    if mode.is_idle():
        return self._execute_idle(forward_batch, pp_proxy_tensors)
    if mode.is_extend(include_draft_extend_v2=True):

    raise ValueError(f"Invalid forward mode for eager runner: {mode}")

4.4RadixAttention and the attention backend zoo

Inside every model, the attention layer is a RadixAttention module (python/sglang/srt/layers/radix_attention.py:91). Despite being an nn.Module, it holds no weights and no kernel — only metadata: tp_q_head_num, tp_k_head_num, head_dim, scaling, layer_id, logit_cap, sliding_window_size, KV scales. @debug_kernel_api
def forward(self, q, k, v, layer: RadixAttention,
            forward_batch: ForwardBatch, save_kv_cache: bool = True, **kwargs):
    """Run forward on an attention layer."""
    if forward_batch.forward_mode.is_idle():
        return q.new_empty(q.shape[0], layer.tp_q_head_num * layer.v_head_dim)
    elif forward_batch.forward_mode.is_decode():

                                   save_kv_cache=save_kv_cache, **kwargs)
    elif forward_batch.forward_mode.is_mixed() and is_npu():
        return self.forward_mixed(...)
    else:

                                   save_kv_cache=save_kv_cache, **kwargs)

Every concrete backend implements forward_decode / forward_extend (writing new K/V into the pool via out_cache_loc, then launching its kernel) plus a strict three-method metadata contract (base_attn_backend.py:19-97):

  • init_forward_metadata(fb) — eager path; by default calls the two below.
  • init_forward_metadata_out_graph(fb, in_capture=False) — host-side per-iteration prep (page tables, indptrs) that runs outside any CUDA graph.
  • init_forward_metadata_in_graph(fb) — static-shape GPU ops recorded inside the graph and auto-replayed; must never call .item()/.cpu().

Backends are chosen by name through a registry (layers/attention/attention_registry.py:31-39): a module-level dict ATTENTION_BACKENDS = {} filled by @register_attention_backend("name") factory functions. A factory can dispatch further — "flashinfer" returns FlashInferAttnBackend or FlashInferMLAAttnBackend depending on runner.use_mla_backend. Unknown names raise ValueError("Invalid attention backend: ...") in model_runner_components/attention_backend_setup.py.

4.5CUDA graphs: making decode launch-bound no more

A decode step runs hundreds of tiny kernels — for small batches, CPU launch overhead dwarfs GPU compute. CUDA graphs fix this by recording the whole forward once per batch-size bucket at startup, then replaying it as a single launch. The design has two orthogonal axes: a phase runner (DecodeCudaGraphRunner, PrefillCudaGraphRunner, EagerRunner — bucket choice, static buffers, output slicing) and a pluggable capture backend (model_executor/runner_backend/): full (one torch.cuda.CUDAGraph per shape), breakable (segmented capture), tc_piecewise (torch.compile FX-split at every attention op), or disabled — configured per phase via --cuda-graph-config, e.g. {"decode": {"backend": "full"}, "prefill": {"backend": "breakable"}} (model_executor/cuda_graph_config.py).

Prefill is no longer eager-only Defaults (cuda_graph_config.py:109-131): decode = full; prefill = breakable on CUDA, tc_piecewise elsewhere. Breakable prefill captures the transformer body once with a single request slot and replays it with live attention metadata; full prefill (opt-in) captures one graph per token-count bucket. Under tc_piecewise, RadixAttention routes through the unified_attention_with_output custom op registered as a split op, so torch.compile cuts the FX graph at every attention call and CUDA-graphs the pieces between them.

Which decode batch sizes get a graph? The default bucket list:

Capture (runner/decode_cuda_graph_runner.py:799) iterates largest batch size first so smaller shapes can reuse the shared graph memory pool, inside freeze_gc (a GC pass mid-capture would poison the graph). Each shape's run_once() is executed twice as warmup, then recorded. At replay time, a real batch is padded up to the nearest bucket: 

@staticmethod
def _pad_to_bucket(raw_size: int, buckets: Sequence[int]) -> int:
    """Return the smallest buckets[i] >= raw_size. ..."""
    assert raw_size <= buckets[-1], (
        f"size {raw_size} exceeds max captured bucket {buckets[-1]}; "
        f"can_run_graph should have rejected this batch"
    )
    index = bisect.bisect_left(buckets, raw_size)
    return buckets[index]

4.6From hidden states to a token

The model trunk produces one hidden state per input token — but for generation we only need logits for the last token of each request. LogitsProcessor (python/sglang/srt/layers/logits_processor.py:340, instantiated inside each model class) prunes before the expensive LM-head matmul: for extend batches, last_index = torch.cumsum(logits_metadata.extend_seq_lens, dim=0) - 1; pruned_states = hidden_states[last_index] (logits_processor.py:525-526). In our §4.2 example that keeps rows [2, 6] of the 7-row hidden-state tensor — the vocab projection runs on 2 rows instead of 7.

4.8Notable facts & gotchas

  • ModelRunner.forward_extend/forward_decode are gone. Dispatch is _forward_raw → runner objects (EagerRunner._execute_*, DecodeCudaGraphRunner, PrefillCudaGraphRunner). The old names survive only on attention backends.
  • CUDA graphs = phase runner × capture backend. Per-phase full | breakable | tc_piecewise | disabled via --cuda-graph-config; decode defaults to full, prefill to breakable on CUDA — prefill is no longer eager-only.
  • Padding invariants: decode replay pads bs to the nearest captured bucket; padded seq_lens lanes hold the backend's seq_len_fill_value ("typically 0 or 1"); outputs are sliced with [: self.raw_num_token]; piecewise prefill explicitly zeroes the padded attention-output tail so NaNs can't leak into residuals or MoE routing.
  • RadixAttention owns zero weights — it's a metadata handle that routes q/k/v to the ambient backend via get_attn_backend() from ForwardContext. Under tc_piecewise it becomes the unified_attention_with_output custom split-op.
  • The metadata contract is three methods (init_forward_metadata / ..._out_graph / ..._in_graph); the legacy init_forward_metadata_capture_cuda_graph / ..._replay_cuda_graph pair is removed.
  • Speculative decoding rides the decode graph: capture mode becomes TARGET_VERIFY with captured_req_width = speculative_num_draft_tokens and a dummy verify-input wired to a static custom_mask buffer (chapter 09).
  • Capture goes largest-shape-first inside freeze_gc, with two warmup runs per shape, and all shapes share one global graph memory pool — that's why graph memory overhead stays modest despite ~60 captured buckets.
  • The Sampler reuses the logits tensor in place (div_ + logits[:] = softmax); grammar masks are applied before sampling in ModelRunner._preprocess_logits and freed immediately to avoid a VRAM leak under overlap scheduling.
  • Model discovery is literal class-name matching against HF architectures[]; unknown architectures fall back to TransformersForCausalLM.
