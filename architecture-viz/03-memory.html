Phase II · The Core Engine

03 · Memory: the KV Cache & RadixAttention

After weights, every byte of GPU memory an inference server owns goes to one thing: the KV cache. This chapter dissects how SGLang stores it (a two-level indirection into per-layer tensors), how it hands slots out (token vs. paged allocators), and its signature idea — RadixAttention, a radix tree over token IDs that lets requests share each other's KV instead of recomputing it.

3.1Why the KV cache is the whole game

During autoregressive decoding, attention at step t needs the key/value vectors of all t−1 previous tokens, for every layer. Recomputing them each step would be quadratic, so they are cached — and that cache is enormous. For a Llama-3-8B-shaped model (32 layers, 8 KV heads, head_dim 128, fp16), one token costs 2 (K+V) × 32 × 8 × 128 × 2 bytes = 128 KiB; a single 8K-token conversation holds ~1 GiB of KV. Whatever GPU memory remains after weights (controlled by --mem-fraction-static) is carved into one giant static KV pool at startup, and the scheduler's entire job (chapter 02) is deciding which requests get to occupy its slots.

Two famous ideas attack two different problems in this space, and they are often confused:

  • PagedAttention (vLLM's contribution) solves fragmentation: instead of reserving one contiguous max-length region per request, KV is allocated in fixed-size pages, so memory can be handed out incrementally with no external fragmentation.
  • RadixAttention (SGLang's contribution) solves recomputation: when two requests share a token prefix — the same system prompt, the same few-shot examples, earlier turns of the same chat — their KV for that prefix is byte-identical. A radix tree keyed on token IDs maps prefixes to already-computed KV slots, so the second request skips prefill for the shared part entirely.
Orthogonal, and SGLang has both Paging is an allocation granularity; prefix reuse is a cache policy. SGLang implements both: --page-size selects the allocation granularity (page_size 1 is fully token-granular), and the radix tree provides prefix reuse on top, with keys truncated to page multiples so a cached prefix is always a whole number of pages. Disabling one (--disable-radix-cache) does not disable the other.

3.2The two-level indirection

SGLang never stores KV "per request". Instead there are two levels of mapping, both plain tensors, so every attention kernel can gather KV with integer indexing:

  • Level 1 — ReqToTokenPool (python/sglang/srt/mem_cache/memory_pool.py:256): an int32 matrix req_to_token of shape (size + 1, max_context_len). Row req_pool_idx belongs to one running request; column p holds the token slot where position p's KV lives. Row 0 is a padding row for CUDA-graph-padded batches.
  • Level 2 — KVCache (memory_pool.py:1581): the physical per-layer tensors. A token slot is a row index into every layer's K and V buffers at once.

Between the two sits the allocator (section 3.3), which owns the free list of token slots. Crucially, nothing says two rows of req_to_token can't point at the same slots — that aliasing is exactly how RadixAttention shares prefixes.

    if need_size > len(self.free_pages):

    select_index = self.free_pages[:need_size]

A page's tokens are always contiguous slots (page × page_size + arange(page_size)), so token slot i belongs to page i // page_size. During batched frees the scheduler brackets work in free_group_begin() / free_group_end() so hundreds of per-request frees coalesce into a single torch.cat; PD-disaggregation setups additionally set need_sort, routing frees into release_pages and lazily re-sorting so allocation order stays ascending.

3.4RadixCache: the tree that shares KV

RadixCache (python/sglang/srt/mem_cache/radix_cache.py:279) maps token-ID prefixes to KV slot indices. It is a true radix (Patricia) tree, not a trie: each edge carries a variable-length token segment, and children are found by a dict probe on the first page of the child's key. Three building blocks:

  • RadixKey — a token-ID array plus an optional extra_key namespace string. Req builds extra_key by concatenating cache_salt and lora_id (managers/schedule_batch.py:888-894), and RadixKey.child_key() prefixes it into the dict key (radix_cache.py:197-207) — so different LoRA adapters or salted requests can never share nodes, without any dedicated per-adapter cache. Prefix comparison (RadixKey.match, line 161) gallops in doubling windows of C-level slice compares, then binary-searches the diverging window — no per-token Python loop.
  • TreeNode (radix_cache.py:216) — fields: children / parent / key; value, an int64 tensor of KV slot indices the same length as the key; lock_ref, a refcount of running requests pinning this node (>0 ⇒ never evicted; the root is created with lock_ref = 1); last_access_time / creation_time / hit_count / priority, which feed the eviction strategies; and the HiCache trio host_value (host-pool indices), host_ref_counter (protect_host() / release_host()) and hash_value (per-page chained SHA256 used as storage keys). Properties: evicted ⇔ value is None (KV only on host), backuped ⇔ host_value is not None.
  • Typed params — every call goes through structs from base_prefix_cache.py: MatchPrefixParams → MatchResult, InsertParams → InsertResult, EvictParams → EvictResult.

match_prefix — the walk that splits nodes

match_prefix page-aligns the key, then walks the tree. If the match ends inside a stored segment, the node is split once at the exact boundary — the tree structurally refines itself as new share-points are discovered: 

def _match_prefix_helper(self, node: TreeNode, key: RadixKey):
    access_time = time.monotonic()
    node.last_access_time = access_time

    child_key = key.child_key(self.page_size)

    value = []
    while len(key) > 0 and child_key in node.children.keys():
        child = node.children[child_key]
        child.last_access_time = access_time
        prefix_len = child.key.match(key, page_size=self.page_size)
        if prefix_len < len(child.key):
            new_node = self._split_node(child.key, child, prefix_len)
            value.append(new_node.value)
            node = new_node
            break
        else:
            value.append(child.value)
            node = child
            key = key[prefix_len:]

            if len(key):
                child_key = key.child_key(self.page_size)

    return value, node

def _split_node(self, key: RadixKey, child: TreeNode, split_len: int):
    # new_node -> child
    # New node inherits child's priority (represents shared prefix)
    new_node = TreeNode(priority=child.priority)
    new_node.hit_count = child.hit_count
    new_node.children = {key[split_len:].child_key(self.page_size): child}
    new_node.parent = child.parent
    new_node.lock_ref = child.lock_ref
    new_node.key = child.key[:split_len]
    new_node.value = child.value[:split_len].clone()
    child.parent = new_node
    child.key = child.key[split_len:]
    child.value = child.value[split_len:].clone()
    new_node.parent.children[key.child_key(self.page_size)] = new_node

    # Split hash_value if it was already computed, otherwise leave as None
    new_node.hash_value, child.hash_value = split_node_hash_value(
        child.hash_value, split_len, self.page_size
    )

    return new_node

insert, lock refs, and the two cache_* entry points

insert() (radix_cache.py:412) walks the same way and returns prefix_len — how many leading tokens were already in the tree. The caller uses that to free its now-duplicate KV slots, because the tree's copy is canonical:

  • cache_finished_req(req) (radix_cache.py:434, called from release_kv_cache in mem_cache/common.py): builds the key from origin_input_ids + output_ids, inserts, then in one free_segments call releases (a) the duplicate range [cache_protected_len, prefix_len) and (b) the page-unaligned tail. Finally dec_lock_ref(req.last_node) drops the request's pin.
  • cache_unfinished_req(req, chunked=True) (radix_cache.py:488, at every chunked-prefill boundary): inserts the prefix so far, frees duplicates, re-runs match_prefix and rewrites the request's own req_to_token row with the canonical tree indices, then migrates the lock: dec_lock_ref(old last_node); inc_lock_ref(new last_node). req.cache_protected_len records how much of the row is now tree-owned so the request never double-frees it.

inc_lock_ref / dec_lock_ref (radix_cache.py:592 / 607) walk node→root; the 0→1 and 1→0 transitions move each node's token count between the evictable_size_ and protected_size_ accumulators the scheduler consults for admission (chapter 02).

Eviction

The cache never scans the tree to evict. It incrementally maintains evictable_leaves — nodes with no un-evicted children and lock_ref == 0 (_update_leaf_status, radix_cache.py:787) — and heapifies that set on demand: 

leaves = list(self.evictable_leaves)
eviction_heap = [
    (self.eviction_strategy.get_priority(node), node) for node in leaves
]
heapq.heapify(eviction_heap)

num_evicted = 0
while num_evicted < num_tokens and len(eviction_heap):
    _priority, x = heapq.heappop(eviction_heap)

    # Tree values are page-aligned copies of a kv row: page-exact segment.
    self.token_to_kv_pool_allocator.free_segment(x.value, start_pos=0)
    num_evicted += len(x.value)
    self._delete_leaf(x)

    if len(x.parent.children) == 0 and x.parent.lock_ref == 0:
        new_priority = self.eviction_strategy.get_priority(x.parent)
        heapq.heappush(eviction_heap, (new_priority, x.parent))

The heap priority comes from a pluggable EvictionStrategy (mem_cache/evict_policy.py): LRUStrategy is simply node.last_access_time; LFUStrategy is (hit_count, last_access_time); SLRUStrategy segments nodes by whether hit_count crossed a protection threshold; PriorityStrategy evicts low-priority requests' nodes first. The CLI exposes --radix-eviction-policy {lru,lfu,slru,priority}; FIFO/MRU/FILO strategies also exist in the file for internal use.

3.6When memory runs out: evict, then retract

Before any allocation, callers run evict_from_tree_cache(tree_cache, num_tokens) (mem_cache/common.py:105): it compares the allocator's available_size() against the need and asks the tree to evict only the shortfall. If decode still cannot fit — every evictable leaf is gone and what remains is locked by running requests — the scheduler escalates to ScheduleBatch.retract_decode (managers/schedule_batch.py:2734): whole requests are popped from the running batch and re-queued, releasing their KV without inserting it into the tree ("we need the space instantly"), and the last survivor is aborted rather than crashing. Chapter 02 covers the retraction policy; the memory-side takeaway is the ownership invariant: every token slot is owned by exactly one of a running request's uncached suffix, the radix tree (evictable or protected), or the allocator free list.

3.7HiCache in one screen: device → host → storage

--enable-hierarchical-cache upgrades the tree so evicting from GPU no longer means recomputing: a TreeNode can hold device slots (value), a host copy (host_value), or exist only as a chain of page hashes (hash_value) in external storage. The data mover is HiCacheController (managers/cache_controller.py:225) — dedicated CUDA streams for device⇄host copies and daemon threads for storage traffic, all polled by the scheduler via tree_cache.check_hicache_events().

Nine L3 backends are registered in mem_cache/storage/backend_factory.py:197-247. Storage keys are per-page SHA256 hashes where each page's hash chains the previous one (get_hash_str, mem_cache/utils.py) — so a key identifies not just a page's tokens but its entire prefix.

Design highlights worth knowing even if you never enable it:

  • Write policies (--hicache-write-policy): plain write_through backs a node up on first hit; write_through_selective waits until hit_count ≥ 2; write_back stages the copy only at eviction time. Backups must keep a contiguous backed-up prefix from the root.
  • Layer-overlapped load-back: host→device copies run layer by layer, ticking a LayerDoneCounter; the forward pass blocks per layer in KVCache.get_key_buffer → layer_transfer_counter.wait_until(layer_id) (memory_pool.py:2233-2239), so prefill starts before the whole prefix has landed.
  • Prefetch discipline: storage prefetch only fires for uncovered suffixes ≥ 256 tokens, is budgeted at half the host pool, and is revoked if the hash lookup hits too little (TP-MIN all-reduced across ranks).

3.9Notable facts & gotchas

  • Slot 0 is a garbage can, on purpose. Every pool allocates size + page_size rows and never hands out page 0; CUDA-graph padded batches default req_pool_indices and out-cache locations to 0, so their dummy writes land harmlessly. ReqToTokenPool has the same trick with row 0.
  • Eviction never scans the tree. evictable_leaves is maintained incrementally on every lock/insert/delete (_update_leaf_status); LRU is just last_access_time as the heap key, and swapping policies swaps only the key function.
  • Page alignment is pervasive. Keys are truncated to page multiples before match/insert, RadixKey.match rounds down to a page, storage hashes are per-page and chained, and free_segment(..., start_pos=…) exploits page contiguity to free with stride arithmetic instead of torch.unique — avoiding a device sync.
  • The tree stores copies, not views. Node values are cloned int64 slices of req_to_token rows; cache_unfinished_req then rewrites the request's row to the canonical indices so duplicate slots can be freed mid-flight.
  • insert() returning prefix_len is a free-list protocol. The return value tells the caller exactly which of its slots became duplicates of existing tree content — freeing them is the caller's job (cache_finished_req / cache_unfinished_req).
  • EAGLE flips keys to bigrams in O(1). RadixKey.maybe_to_bigram_view just sets a flag; draft-model caches key on token pairs without materializing tuple lists (chapter 09).
  • Prefix compare is gallop + binary search. RadixKey.match does C-level array slice compares in doubling windows — matching a 10K-token shared prefix costs ~log² slice comparisons, not 10K Python iterations.
  • fp8 KV is uint8 at rest because index_put lacks float8 support; buffers are re-view()-ed on read.
  • Deterministic mode skips finished-request inserts (disable_finished_insert in RadixCache) — cache hits change batch composition, which can change results under non-deterministic kernels.
