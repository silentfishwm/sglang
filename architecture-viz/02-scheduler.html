Phase II · The Core Engine

02 · The Scheduler — Continuous Batching & Policies

The Scheduler is SGLang's heartbeat: a per-GPU-rank process that, every few milliseconds, decides which requests prefill, which decode, and which get thrown back in the queue when memory runs out. This chapter walks the real event loop, the request state machine, the token-budget admission math, and the overlap trick that hides all CPU work behind GPU compute.

2.1Why continuous batching exists

Classic serving systems batched at request granularity: collect N prompts, run all of them to completion, return. That wastes enormous GPU time — a request that finishes after 10 tokens sits idle while its batchmate generates 2,000. The fix, introduced by Orca (OSDI '22) as iteration-level scheduling and now universal (vLLM, SGLang, TensorRT-LLM), is continuous batching: the scheduler re-decides batch membership every forward pass. Finished requests leave immediately; waiting requests join as soon as memory allows; one iteration might be a prefill, the next a decode of a completely different composition.

In SGLang this loop lives in python/sglang/srt/managers/scheduler.py (the Scheduler class — one instance per TP rank, running inside the GPU subprocess you met in chapter 01). Its two central data structures:

  • self.waiting_queue: List[Req] — requests admitted by handle_generate_request but not yet running.
  • self.running_batch: ScheduleBatch — the persistent decode pool. Requests enter it after their prefill completes and stay until they finish or get retracted.

recv_requests: rank 0 pulls ZMQ messages and broadcasts them to other TP ranks via a gloo group. get_next_batch_to_run returns a NextBatchPlan (a msgspec Struct with exactly two fields, batch_to_run and running_batch — schedule_batch.py:3283). Idle iterations call on_idle() instead of run_batch.

The subtle part is the merge: how does a prefill batch "become" decode? It doesn't — last iteration's EXTEND batch is folded into running_batch at the top of the next get_next_batch_to_run, after dropping requests that already finished (a single-token answer can finish during its own prefill) and the still-in-flight chunked request: 

# Filter batch
last_bs = last_batch.batch_size()
last_batch.filter_batch(chunked_req_to_exclude=list(chunked_req_to_exclude))
if last_batch.batch_size() < last_bs:
    running_batch.batch_is_full = False

# Merge the new batch into the running batch.
if not last_batch.is_empty():
    if running_batch.is_empty():
        running_batch = last_batch
    else:
        # Merge running_batch with prefill batch
        running_batch.merge_batch(last_batch)
"running_batch" is not what runs self.running_batch is the persistent decode pool. The object actually forwarded each iteration is plan.batch_to_run, which may be a fresh EXTEND batch, the filtered + prepare_for_decode'd running batch, a MIXED batch (§2.8), or a DP-attention IDLE batch injected by dp_attn_adapter.maybe_prepare_mlp_sync_batch so all DP ranks step together.

2.5Scheduling policies — who goes first?

Before admission, self.policy.calc_priority(self.waiting_queue, running_batch) (scheduler.py:3080) sorts the waiting queue in place. The policy comes from --schedule-policy (server_args.py:796-811, default "fcfs") and resolves to one of two enum families in schedule_policy.py:

CLI valueEnumBehavior
fcfs (default)CacheAgnosticPolicy.FCFS Arrival order. With --enable-priority-scheduling, sorts by (priority × sign, wait_queue_entry_time) instead.
lpmCacheAwarePolicy.LPM Longest-prefix-match: requests with the biggest radix-cache hit first, maximizing KV reuse. Auto-degrades to FCFS when the queue exceeds 128 requests (_determine_active_policy, schedule_policy.py:239-243).
dfs-weightCacheAwarePolicy.DFS_WEIGHT Weights radix-tree nodes by descendant request count and emits requests in DFS order of the heaviest subtrees — batches cache-sharing siblings together.
lofCacheAgnosticPolicy.LOF Longest output first (by max_new_tokens).
randomCacheAgnosticPolicy.RANDOMShuffle.

The "priority" gotcha "priority" appears in the --schedule-policy choices, but SchedulePolicy._validate_and_adjust_policy only accepts lpm / dfs-weight / fcfs / lof / random / routing-key and raises ValueError for anything else. Real priority scheduling is a layer: --enable-priority-scheduling on top of fcfs or lof (asserted at server_args.py:8636-8639). Any cache-aware policy also silently degrades to FCFS if the radix cache is disabled. 
@staticmethod
def _sort_by_longest_prefix(
    waiting_queue: List[Req], temporary_deprioritized: Set[int]
) -> None:
    """Sorts the waiting queue based on the longest prefix match."""
    waiting_queue.sort(
        key=lambda r: (
            -r.num_matched_prefix_tokens
            if r.rid not in temporary_deprioritized
            else float("inf")
        )
    )

temporary_deprioritized implements in-batch prefix caching (_compute_prefix_matches, schedule_policy.py:263): each pass builds a throwaway simulated radix tree over the waiting queue itself. A request with a small real-cache hit (≤ 32 tokens) that shares ≥ 32 tokens with another queued request is pushed to the back — one representative runs first and warms the cache for its siblings.

2.6PrefillAdder — the token-budget bouncer

Sorting decides order; PrefillAdder (schedule_policy.py:444) decides how many. get_new_batch_prefill constructs one per pass (scheduler.py:3097) and feeds it the queue head-first via adder.add_one_req(req, ...) until a budget runs dry. Four budgets, two failure modes:

2.7Retraction — when the decode gamble fails

Admission is probabilistic on purpose: rem_total_tokens discounts each running request's remaining max_new_tokens by new_token_ratio (init 0.7 × schedule_conservativeness, decaying toward 0.7 × 0.14 ≈ 0.098 over 600 retraction-free steps — NewTokenRatioTracker, values from environ.py:395-397). Most requests stop early, so betting on that packs more in. When the bet fails, update_running_batch notices (not batch.check_decode_mem(), scheduler.py:3331) and calls retract_decode — evicting decode requests back to the waiting queue: 

retracted_reqs = []
first_iter = True
while first_iter or (
    not self.check_decode_mem(selected_indices=sorted_indices)
):
    if len(sorted_indices) == 1:
        # Always keep at least one request
        break

    first_iter = False
    idx = sorted_indices.pop()
    req = self.reqs[idx]
    retracted_reqs.append(req)
    # release memory and don't insert into the tree because we need the space instantly
    self.release_req(idx, len(sorted_indices), server_args)

reqs_to_abort: List[Req] = []
if len(sorted_indices) <= 1 and not self.check_decode_mem(
    selected_indices=sorted_indices
):
    # Even the last remaining request cannot fit in memory.
    # Instead of crashing the scheduler, gracefully abort it.
    last_idx = sorted_indices.pop()

  • Who gets evicted: _get_decode_retraction_order — with the default --retraction-policy length, victims are popped from the tail of a sort by (len(output_ids), -len(origin_input_ids)): fewest generated tokens (least sunk cost) and longest prompts (biggest memory refund) go first. "priority" sorts by request priority first.
  • What eviction does: req.reset_for_retract() (schedule_batch.py:1603) zeroes prefix_indices, extend_range, kv_committed_len … but keeps output_ids — on re-admission the request re-prefills prompt + everything generated so far, usually recovering most KV from the radix cache.
  • Feedback loop: the returned new_token_ratio estimate is written back to the tracker (scheduler.py:3366), making future admission more conservative; each retraction-free decode step decays it back down (decay_step).
  • Graceful degradation: if even one lone request cannot decode, it gets a FINISH_ABORT with HTTP 500 and an AbortReq is pushed to the tokenizer — a deliberate change from older assert-crash behavior. Demo hook: SGLANG_TEST_RETRACT=1 forces retraction every few forwards.

2.8Chunked prefill & mixed batches

A 100k-token prompt prefilled in one go would stall every decoding request for seconds. Chunked prefill caps each pass at rem_chunk_tokens; the scheduler holds the split request as self.chunked_req and bumps req.inflight_middle_chunks (scheduler.py:3223-3224). The chunk cycle, per iteration:

  1. get_next_batch_to_run excludes chunked_req from the running-batch merge and calls stash_chunked_request — committing the finished chunk's KV into the radix tree via maybe_cache_unfinished_req(..., chunked=True).
  2. get_new_batch_prefill: chunked_req.init_next_round_input() re-matches the prefix (now covering all finished chunks!), then adder.add_chunked_req(...) re-admits the next window before any queued request (scheduler.py:3115-3117).
  3. Middle-chunk results are drained without streaming (inflight_middle_chunks -= 1 in the result processor); when add_chunked_req finds the remainder fits (truncated == False, schedule_policy.py:917) it returns None, chunked_req clears, and the final chunk samples the first token like a normal prefill.

With --enable-mixed-chunk, the leftover chunk budget is spent on decode: the running batch is folded into the prefill forward as a single ForwardMode.MIXED batch (scheduler.py:3272-3287), so decode never stalls behind chunks: 

def mix_with_running(self, running_batch: ScheduleBatch):
    self.forward_mode = ForwardMode.MIXED
    running_bs = running_batch.batch_size()

    for req in running_batch.reqs:
        req._refresh_fill_ids()
        full_len = len(req.full_untruncated_fill_ids)
        req.set_extend_range(full_len - 1, full_len)

    # Decode tokens of the running portion live in future_map.output_tokens_buf.
    self.input_ids = None
    self.mix_running_indices = running_batch.req_pool_indices
    out_cache_loc = torch.cat([self.out_cache_loc, running_batch.out_cache_loc])

Two small governors blunt the prefill-first bias in special setups: PrefillDelayer (managers/prefill_delayer.py) is a DP-synchronized negotiation that delays prefill until all DP-attention ranks can prefill together (or a watermark/max-delay hits), protecting decode latency; MinFreeSlotsDelayer.should_delay (running_bs, num_allocatable_reqs) (managers/min_free_slots_delayer.py) holds fresh admissions until several request slots are free so expensive admissions batch into one — always-on for DFlash via the formula min(4, max(2, (max_running_requests + 5) // 6)).

2.9Overlap scheduling — hiding the CPU behind the GPU

Everything above — queue sorting, budget math, radix matching, detokenizer IPC — is CPU work. Done naively it serializes with GPU compute: forward, wait, process, forward. The default event_loop_overlap instead runs the scheduler on a dedicated schedule_stream and launches each forward on a separate forward_stream without waiting, then processes the previous iteration's result while the GPU crunches the current one: 

# Launch the current batch
if batch:
    batch_result = self.run_batch(batch)
    # Fence result processing behind this forward's shared reads.
    self._apply_war_barrier()
    self.result_queue.append((batch.copy(), batch_result))
else:
    batch_result = None

# Process the last batch
if self.last_batch:
    if not disable_overlap_for_batch:
        pop_and_process()
elif batch is None:
    # When the server is idle, do self-check and re-init some states
    self.on_idle()

# Run sample of the current batch
if self.is_generation:
    self.launch_batch_sample_if_needed(batch_result, batch)

# Update last_batch
self.last_batch = batch

But there's a paradox: to schedule decode step N+1 you need step N's sampled tokens — which don't exist on the CPU yet. This repo's answer is the FutureMap (managers/overlap_utils.py), a pool-indexed GPU-side relay: run_batch stashes the sampled tokens into future_map.output_tokens_buf at req_pool_indices (_relay_forward_payload, scheduler.py:3707) and sets batch.input_ids = None (scheduler.py:3583). At the next forward's entry, the input ids are gathered on-GPU — the CPU never touches them:

The result_queue holds exactly the in-flight batch, so all CPU result processing for batch N−1 hides behind batch N's GPU time. In CI (_DEBUG_ASSERT) the token buffer rows are poisoned with −1 and every gather asserts non-negative then re-poisons — a consume-once discipline that catches "gather without stash" bugs. Overlap is selectively disabled for two consecutive prefills or when a grammar FSM must sync (is_disable_overlap_for_batch, scheduler.py:1735).

This design leaks into batch preparation: because the launched forward holds references to the batch's tensors, prepare_for_decode must rebind fields out of place instead of mutating them (see the project rule on ScheduleBatch mutation):

Two more overlap layers exist beyond this loop: non-token values relay through FutureMap.publish + pinned D2H on a private stream (resolve_seq_lens_cpu), and record_batch_in_overlap pins each launched batch plus a field snapshot in a 2-slot ring so GPU tensors survive the caching allocator across streams (scheduler.py:3406). Orthogonal to all of it is two-batch overlap (batch_overlap/two_batch_overlap.py), which splits one forward into two micro-batches to hide MoE all-to-all communication — that story is chapter 09.

2.10Notable facts & gotchas

  • Prefill starves decode by design. If any EXTEND batch can be formed, decode waits (scheduler.py:2977-2986). --enable-mixed-chunk, PrefillDelayer and MinFreeSlotsDelayer all exist to blunt this bias.
  • Finish is two-phase. finished_reason is set and KV freed (release_kv_cache) in the result processor, but the req stays in running_batch.reqs until the next filter_batch(). Code walking running reqs must skip req.finished().
  • Overlap runs one iteration behind — a finished or retracted request may receive one extra speculative decode step whose over-allocated tokens are freed later; and mix_with_running uses delta = 0 if enable_overlap else -1 because output_ids lags one step.
  • batch_is_full is a sticky optimization flag, reset whenever requests leave the batch — not a live measurement.
  • Budgets double-book the radix cache: rem_total_tokens counts evictable_size() as free, so admission may rely on evicting cached prefixes; the actual eviction happens later in alloc_for_extend / check_decode_mem.
  • The chunked request is never merged into running_batch mid-flight — it's explicitly excluded, and its per-chunk KV committed to the radix tree between chunks is exactly what makes the next chunk's prefix match work.
  • Health checks are load-shedded: a health-check generate request is dropped with a canned reply whenever the server is busy (scheduler.py:1788).
  • Defaults cheat sheet: --schedule-policy fcfs · --max-prefill-tokens 16384 · --chunked-prefill-size auto by GPU memory tier (−1 disables) · --schedule-conservativeness 1.0 · --retraction-policy length · --priority-scheduling-preemption-threshold 10 · overlap ON unless --disable-overlap-schedule · mixed chunk OFF unless --enable-mixed-chunk · CLIP_MAX_NEW_TOKENS 4096.
