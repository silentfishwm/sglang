11 · The Front Door: Language DSL, CLI, Benchmarks & Tests

Chapters 01–10 lived inside the server. This chapter covers everything that stands in front of it: the original SGLang frontend language (the project's namesake), the sglang CLI, the benchmarking & eval toolchain that defines the numbers everyone quotes (TTFT, TPOT, ITL), and the CI/test machinery that keeps 95 workflows honest.

11.1The original "SGLang": a language, not a server

The project name stands for Structured Generation Language — before SGLang was a famous inference engine, it was a Python-embedded DSL for programming multi-call LLM workflows (the NeurIPS 2024 paper "SGLang: Efficient Execution of Structured Language Model Programs" describes both halves: the frontend language and the RadixAttention runtime). The language still ships in python/sglang/lang/ and is worth understanding for two reasons: it is the cleanest demonstration of why the server has features like radix prefix caching and zero-token logprob scoring, and several root-level benchmarks (benchmark/gsm8k, benchmark/tree_of_thought_deep, …) are written in it.

A program is an ordinary Python function decorated with @sgl.function (lang/api.py), whose first argument must literally be named s — enforced by assert argspec.args[0] == "s", 'The first argument must be "s"' in SglFunction.__init__ (lang/ir.py:149). The body builds a prompt by +=-ing expressions onto s. Plain strings become SglConstantText; the full IR vocabulary in lang/ir.py is: SglGen, SglSelect, SglConstantText, SglExprList, SglArgument, SglImage, SglVideo, SglRoleBegin/SglRoleEnd, SglVariable, SglVarScopeBegin/SglVarScopeEnd, SglFork, SglGetForkItem, SglConcateAndAppend, SglCommitLazy, and SglSeparateReasoning.

The crucial design decision: there is no compile step in the normal path. Your Python function executes eagerly, but every s += expr (ProgramState.__iadd__) just submits the IR node to a StreamExecutor — "a stream executor that executes SGL expressions in a background thread" (its docstring, interpreter.py:274). Your code returns immediately; generation streams asynchronously; and reading state["answer"] blocks on a per-variable threading.Event. It's a futures system disguised as string concatenation: 

def submit(self, expr: SglExpr):
    self._init_var_event(expr)

    if self.use_thread:
        self.queue.put(expr)
    else:
        self._execute(expr)

def sync(self):
    if self.use_thread:
        self.queue.join()

def get_var(self, name):
    if name in self.variable_event:
        self.variable_event[name].wait()
    return self.variables[name]

The worker thread pops nodes and dispatches on type — a plain isinstance chain, no visitor pattern, no bytecode: 

if isinstance(other, SglConstantText):
    self._execute_fill(other.value)
elif isinstance(other, SglGen):
    self._execute_gen(other)
elif isinstance(other, SglSelect):
    self._execute_select(other)
elif isinstance(other, SglExprList):
    for x in other.expr_list:
        self._execute(x)
elif isinstance(other, SglRoleBegin):
    self._execute_role_begin(other)
elif isinstance(other, SglRoleEnd):
    self._execute_role_end(other)
Where the tracer fits A separate lang/tracer.py can build a static graph by running the function against a tracing state — that's what the SglFork/SglGetForkItem IR nodes exist for. Live execution never uses them (forking clones executors instead, §11.3). Tracing is used by cache_program (interpreter.py): when run_batch gets more than one argument set and global_config.enable_precache_with_tracing is on, it extracts the constant prompt prefix shared by the whole batch and pre-caches it on the server (only if longer than 64 chars).

Runtime vs Engine sgl.Runtime spawns a full HTTP server subprocess and polls /health_generate until it's up — it is the frontend's way of getting a server without a terminal (runtime_endpoint.py:356). It is explicitly distinct from sgl.Engine, the in-process offline engine from chapter 01. Streaming reads work per variable: state.text_iter("answer") yields chunks as stream_var_event fires.

Why start two tokens early? Appending "Paris" to the prompt can merge with the prompt's last token during retokenization ("token healing"). Starting logprobs at prompt_len - 2 captures the boundary token; afterwards the code checks whether s.text_ still ends with that token's text and, if so, arithmetically removes its logprob from the normalized mean (runtime_endpoint.py:283-292) so unhealed choices aren't penalized.

11.3fork/join and server-side KV reuse

state.fork(2) makes the parent executor sync(), then constructs two brand-new StreamExecutors — each with its own queue and worker thread — copying variables, text_, messages_, and recording fork_start_text_pos = len(self.text_) (interpreter.py:370-402). The returned ProgramStateGroup broadcasts += to every branch (a lambda receives the branch index). join() has two modes (interpreter.py:1052):

  • "gather_variable" (default) — sync each child, then copy variables the children created back into the parent as lists.
  • "concate_and_append" — the parent submits SglConcateAndAppend. If global_config.enable_parallel_encoding is on and the backend advertises support_concate_and_append, the interpreter asks the backend to merge the branches' KV caches server-side: RuntimeEndpoint.concatenate_and_append posts {"src_rids": [...], "dst_rid": ...} to /concate_and_append_request (runtime_endpoint.py:317-324). Otherwise it falls back to plain text concatenation.
Legacy endpoint alert /concate_and_append_request exists only on the client side in this repo — no route in python/sglang/srt/ implements it anymore, so the KV-merge join is a legacy path from the paper era that would 404 against today's server. In practice you don't miss it: because every forked branch shares the parent's prefix (fork_start_text_pos), the RadixAttention tree from chapter 03 deduplicates the shared prefix KV automatically when the branches' /generate calls land — fork/join parallelism gets prefix reuse for free.

serving.py is adapted from vLLM's benchmark_serving.py (credited in its header) and supports 10+ API flavors via ASYNC_REQUEST_FUNCS (sglang, sglang-oai, sglang-oai-chat, vllm, trt, lmdeploy, …). one_batch.py's docstring: "Benchmark the latency of running a single static batch without a server" — it reports prefill latency/throughput and per-step decode latency, plus a --correct mode that prints reference logits.

Load is generated as a Poisson process: exponential inter-arrival times with mean 1/request_rate. This matters — real traffic is bursty, and a fixed-interval load generator would flatter the scheduler: 

if request_rate == float("inf"):
    # If the request rate is infinity, then we don't need to wait.
    continue

# Sample the request interval from the exponential distribution.
interval = np.random.exponential(1.0 / request_rate)
# The next request will be sent after the interval.
await asyncio.sleep(interval)

Why "retokenized" ITL? With speculative decoding (chapter 09) one streamed chunk can carry several accepted tokens, so raw chunk gaps overstate per-token latency. When accept_length > 0 and the backend is sglang-oai[-chat], each gap is divided by the chunk's retokenized token count. Every metric is reported as mean / median / std / p90 / p95 / p99.

Every test class extends CustomTestCase, which fixes a real unittest footgun for GPU tests: if setUpClass raises (say, the server fixture fails to boot), stock unittest never calls tearDownClass — leaking ports and GPU-holding processes that poison every later test on the runner: 

class CustomTestCase(unittest.TestCase):

    def __init_subclass__(cls, **kwargs):
        super().__init_subclass__(**kwargs)

        # Wrap the effective setUpClass so that tearDownClass is called
        # even when setUpClass fails. Python's unittest skips tearDownClass
        # if setUpClass raises, which can leak resources (ports, processes).
        setup = cls.setUpClass
        if getattr(setup, "_safe_setup_wrapped", False):
            return
Failfast by default The suite runner executes each file as python file.py -f, so test files must end with plain unittest.main() (or pytest.main([__file__])). The wrapper also calls _wait_for_gpu_idle_in_ci() before setup, so a test never starts while the previous one's server is still releasing VRAM. Suites per commit are enumerated in PER_COMMIT_SUITES (run_suite.py) and nightlies in NIGHTLY_SUITES. Non-CI experiments belong in test/manual/.

11.8Notable facts & gotchas

  • The DSL is a futures system in disguise. s += expr is a queue put; state["var"] is threading.Event.wait(). No graph, no compiler — tracer.py exists but is only used for batch prefix pre-caching and SglFunction.trace().
  • run_batch defaults to max(96, cpu_count()*16) client threads (interpreter.py:110) — the frontend leans entirely on the server's continuous batching for efficiency.
  • select() never generates a token. It's 2–3 max_new_tokens=0 logprob requests, batched over prompt+choice, with token-healing correction starting at prompt_len − 2.
  • num_api_spec_tokens is client-side speculation. @sgl.function(num_api_spec_tokens=128) makes the OpenAI backend over-generate once and _spec_gen slice the text across later gen() calls — saving API round-trips. Completely unrelated to chapter 09's server-side speculative decoding.
  • /concate_and_append_request is client-only now — the srt server no longer implements it; radix caching (chapter 03) provides fork-prefix reuse instead.
  • TPOT is derived, ITL is measured. TPOT = (latency − ttft)/(output_len − 1); ITL is per-chunk. With spec decoding, bench_serving divides chunk gaps by retokenized token counts.
  • sglang.bench_serving et al. are deprecation shims over sglang.benchmark.*, kept alive with FutureWarnings because the whole ecosystem's muscle memory types them.
  • CI tests self-declare their cost: est_time in register_cuda_ci(...) feeds run_suite.py's auto-partitioner, which bin-packs files across parallel jobs to keep every job under ~30 minutes.
  • global_config.py is marked for death — its own header says "FIXME: deprecate this file and move all usage to sglang.srt.environ or sglang.__init__.py"; it now only holds frontend-language knobs.
  • version.py has a 4-level fallback: setuptools-scm generated _version.py → importlib.metadata → live setuptools_scm.get_version() → "0.0.0.dev0".
