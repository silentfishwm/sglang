Phase III · Models & Compute

06 · The Kernel Stack: AOT, JIT, Triton, torch.compile & Hardware Backends

Every matmul, norm, and attention call in chapters 04–05 eventually bottoms out in a kernel. SGLang keeps four in-tree implementation tiers (prebuilt CUDA wheel, JIT-compiled CUDA, Triton, pure torch) plus external libraries, and picks between them per-op, per-device, at runtime. This chapter maps that machinery: the unified sglang.kernels package, the backend-selection contract, torch.compile with piecewise CUDA graphs, deterministic batch-invariant ops, and how seven hardware families plug into one codebase.

6.1One package: sglang.kernels (RFC #29630)

Historically SGLang shipped kernels from a separate repo-root sgl-kernel/ project plus a scattered sglang.jit_kernel package. In this repo both are gone: everything was unified under python/sglang/kernels/.

Renames to keep straight The old repo-root sgl-kernel/ tree now lives at python/sglang/kernels/aot/. Its wheel is published as sglang-kernel ("prior sgl-kernel"), but "the Python import path remains sgl_kernel" (python/sglang/kernels/aot/README.md). The legacy sglang.jit_kernel package was removed in the RFC finale (#32072): its build infra moved to sglang.kernels.jit, and each JIT op into sglang.kernels.ops.<group>._jit_<op>. If you read upstream docs mentioning sgl-kernel/ at the repo root — this repo wins.

Rough division of labor: AOT for heavyweight kernels needing CUTLASS or big C++ deps (stable wheel boundary, broadest shape support — the default for public wrappers); JIT is preferred for new kernels that don't need CUTLASS (.claude/skills/add-jit-kernel); Triton is the portability tier (CUDA/ROCm/XPU); torch native is the correctness oracle every other backend is parity-tested against (test/registered/kernels/).
Import stays cheap register_kernel(KernelSpec(...)) records metadata only — an operator id like "layernorm.rmsnorm", a backend, and a "module:attr" import path. No torch, no sgl_kernel, no JIT compile happens until a kernel is actually called (KernelSpec.load() is lazy), so import sglang.kernels works on a CPU-only box.

6.2The backend spectrum & auto-selection

A crucial subtlety baked into the type system: KernelBackend names the provenance of an implementation (how it is built), not the hardware it runs on. Both JIT and AOT sources build for CUDA and ROCm; which devices a given op supports is per-(op, backend) metadata (CapabilityRequirement): 

class KernelBackend(str, Enum):
    """Provenance of a kernel implementation (how it is built), not its device."""

    TORCH = "torch"  # pure-torch reference (forward_native)
    TORCH_COMPILE = "torch_compile"  # torch.compile(forward_native)
    TRITON = "triton"
    JIT = "jit"  # sglang.kernels.jit (nvcc / hipcc)
    AOT = "aot"  # sgl_kernel wheel (CUDA / ROCm builds)
    CUTE_DSL = "cute_dsl"
    FLASHINFER = "flashinfer"
    DEEPGEMM = "deepgemm"
    AITER = "aiter"  # AMD aiter library (device=HIP)
    TORCH_NPU = "torch_npu"  # Ascend NPU vendor runtime (device=NPU)

Plain registry ops have no heuristic ranking — select_kernel() resolves a single-backend op directly, and multi-backend ops must be pinned by name. The richer contract is BaseFusedOp (currently the layernorm and activation groups): one logical operator, one forward_<backend> method per backend, all behind one forward(). forward_native is required; forward_torch_compile is inherited for free as torch.compile(forward_native); everything else is opt-in.

6.4The JIT tier: TVM-FFI + a content-addressed cache

JIT kernels are header-only .cuh templates under python/sglang/kernels/jit/csrc/, compiled on first call through TVM-FFI (tvm_ffi.cpp.load / load_inline) and exported via generated TVM_FFI_DLL_EXPORT_TYPED_FUNC wrapper lines. The killer feature is that C++ template specialization is chosen from Python: make_cpp_args() turns a torch dtype and flags into a C++ template argument string, so one .cuh serves every dtype/arch combination without a single runtime branch on the device: 

def _fast_math_flags() -> list[str]:
    # Mirrors sgl-kernel's CMake policy: fast-math on SM90, precise on
    # SM100+ (Blackwell needs bit-exact expf), off on HIP (clang rejects).
    if is_hip_runtime():
        return []
    if get_jit_cuda_arch().major >= 10:
        return []
    return ["--use_fast_math"]

6.6Batch-invariant ops: buying determinism

Why is LLM inference nondeterministic even at temperature 0? Because cuBLAS/cuDNN pick different reduction strategies for different batch sizes, and floating-point addition is not associative — the same request batched with 3 neighbors vs 30 produces bitwise-different logits. --enable-deterministic-inference fixes this by hot-swapping the guilty ATen ops process-wide with Triton kernels that use a fixed reduction order (adapted from Thinking Machines' batch_invariant_ops). The swap is wired in ModelRunner.maybe_enable_batch_invariant_mode() (model_runner.py:714) and uses the torch dispatcher itself: 

def enable_batch_invariant_mode(enable_bmm: bool = True):
    global _batch_invariant_MODE, _batch_invariant_LIB, _original_torch_bmm
    if _batch_invariant_MODE:
        return

    dispatch_key = get_dispatch_device_backend()

    _batch_invariant_MODE = True
    _batch_invariant_LIB = torch.library.Library("aten", "IMPL")

    if not _is_npu:
        # Register for detected device
        _batch_invariant_LIB.impl("aten::mm", mm_batch_invariant, dispatch_key)
        _batch_invariant_LIB.impl("aten::addmm", addmm_batch_invariant, dispatch_key)
        _batch_invariant_LIB.impl(
            "aten::_log_softmax", _log_softmax_batch_invariant, dispatch_key
        )
        _batch_invariant_LIB.impl("aten::mean.dim", mean_batch_invariant, dispatch_key)
        _batch_invariant_LIB.impl("aten::rms_norm", _rms_norm_aten_compat, dispatch_key)
        _batch_invariant_LIB.impl("aten::mm.dtype", _mm_dtype_compat, dispatch_key)

        if enable_bmm:
            _batch_invariant_LIB.impl("aten::bmm", bmm_batch_invariant, dispatch_key)
            # Also monkeypatch torch.bmm directly as a fallback
            _original_torch_bmm = torch.bmm
            torch.bmm = bmm_batch_invariant

The replacements are persistent Triton kernels (matmul_kernel_persistent, bmm_kernel_persistent, _log_softmax_kernel, mean_kernel, _rms_norm_kernel); matmul can route to DeepGEMM when eligible. The RMSNorm shows the trick — one program per row, columns reduced in a fixed sequential loop, so the summation order never depends on batch size:

@triton.jit
def _rms_norm_kernel(
    input_ptr,
    weight_ptr,
    output_ptr,
    input_row_stride: tl.constexpr,
    output_row_stride: tl.constexpr,
    n_cols: tl.constexpr,
    eps,
    BLOCK_SIZE: tl.constexpr,
):
    row_idx = tl.program_id(0).to(tl.int64)
    row_start_ptr = input_ptr + row_idx * input_row_stride
    output_row_start_ptr = output_ptr + row_idx * output_row_stride

    # Step 1: Compute sum of squares in float32 to avoid overflow
    sum_sq = tl.zeros([1], dtype=tl.float32)
    for col_offset in range(0, n_cols, BLOCK_SIZE):
        col_idx = col_offset + tl.arange(0, BLOCK_SIZE)
        mask = col_idx < n_cols

        vals = tl.load(row_start_ptr + col_idx, mask=mask, other=0.0)
        # Convert to float32 for accumulation to prevent overflow
        vals_f32 = vals.to(tl.float32)
        sq_vals = vals_f32 * vals_f32
        sum_sq += tl.sum(tl.where(mask, sq_vals, 0.0))

Even collectives: ROCm ships a dedicated deterministic_all_reduce.hip in the AOT tree. srt/hardware_backend/ is the code drop zone — per-vendor implementation trees: cpu/ & gpu/ (AWQ/GPTQ quant kernels), npu/ (five Ascend attention backends, NPU graph runners including EAGLE draft runners, its own allocator/memory pool), xpu/ (graph runner + Triton FLA kernels), musa/, and mlx/ — a full parallel stack for Apple Silicon with its own model_runner.py, tp_worker.py, scheduler_mixin.py, KV-cache pool and fused SwiGLU MoE. MPS is made viable by two root-level shims: sglang/_mps_stub.py patches missing torch.mps APIs, and sglang/_triton_stub.py installs a mock triton module whose @triton.jit is a pass-through decorator so Triton-importing modules load on macOS (the kernels are never executed there).

6.8Notable facts & gotchas

  • The wheel/import split trips everyone: pip package sglang-kernel, source tree python/sglang/kernels/aot/, import path sgl_kernel, dispatcher namespace torch.ops.sgl_kernel.* — four names, one artifact.
  • 85 op schemas in the CUDA common_extension.cc alone; ROCm and MUSA have their own extension files, so per-platform wheels expose different op subsets — which is why CapabilityRequirement is per-(op, backend), not per-backend (sgl_kernel builds silu_and_mul for ROCm but not rmsnorm).
  • The AOT wheel compiles other projects' sources into itself: flashinfer's norm.cu/renorm.cu and flash-attention sparse kernels are built straight into sgl_kernel at pinned commits (CMakeLists.txt:298–305).
  • JIT fast-math policy is arch-aware: fast-math on SM90, precise on SM100+ ("Blackwell needs bit-exact expf"), off on HIP (clang rejects the flag) — ops/activation/activation.py:22.
  • weak_ref_tensor exists twice — C++ in the AOT tree (csrc/memory/weak_ref_tensor.cpp) and Python in srt/compilation/weak_ref_tensor.py: the trick that lets CUDA-graph outputs be aliased without extending tensor lifetimes.
  • Speculative tree verification defaults to deterministic: tree_speculative_sampling_target_only(..., bool deterministic = true) (csrc/speculative/speculative_sampling.cu:31) — see chapter on speculative decoding.
  • Piecewise never crashes the scheduler: a Dynamo mid-serving recompile without a capture stream logs a warning and runs that subgraph eagerly (cuda_piecewise_backend.py).
  • split_module(keep_original_order=True) is load-bearing — the FX graph contains mutations (in-place attention output), and reordering would change semantics (comment at backend.py:243).
  • IDE support for JIT headers is generated: python -m sglang.kernels.jit writes a .clangd file so the header-only .cuh tree gets completion and diagnostics.
  • Heavy header-only deps are pluggable for JIT: @register_dependency("flashinfer") (jit/utils/deps.py:31) resolves include paths out of the installed flashinfer wheel — the sanctioned way for a JIT kernel to use CUTLASS without moving to the AOT tier.
