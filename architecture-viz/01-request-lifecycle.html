01 · Processes & the Life of a Request

Before diving into any subsystem, you need the skeleton: which OS processes exist, how they talk over ZMQ, and exactly what happens between an HTTP request arriving and tokens streaming back. Everything else in this guide hangs off this picture.

1.1The three-role architecture

An SGLang server is a small constellation of processes with three roles. Only one of them touches the GPU:

  • Main process — runs the uvicorn/FastAPI HTTP server and the TokenizerManager. Important: TokenizerManager is a Python object living inside the main process, not a separate process (stated explicitly in the docstring at python/sglang/srt/entrypoints/engine.py).
  • Scheduler subprocesses — one per GPU rank. Each Scheduler embeds a TpModelWorker, which embeds a ModelRunner — so the model executor runs inside the scheduler process. There is no separate "worker process".
  • Detokenizer subprocess — one DetokenizerManager that turns token IDs back into UTF-8 text incrementally.

1.2The ZMQ wiring

All cross-process traffic flows over ZMQ sockets whose endpoints are minted once in PortArgs.init_new() (python/sglang/srt/server_args.py) — normally ipc://<tempfile> unix sockets, or TCP ports derived from dist_init_addr when --enable-dp-attention is on (port delta constant ZMQ_TCP_PORT_DELTA = 233).

PortArgs fieldDirectionPayloads
scheduler_input_ipc_name TokenizerManager binds PUSH → Scheduler rank-0 connects PULL TokenizedGenerateReqInput, BatchTokenizedGenerateReqInput, control reqs (AbortReq, FlushCacheReqInput, ProfileReq, …)
detokenizer_ipc_name Scheduler rank-0 PUSH → Detokenizer binds PULL BatchTokenIDOutput, BatchEmbeddingOutput
tokenizer_ipc_name Detokenizer PUSH (and Scheduler PUSH for control replies) → TokenizerManager binds PULL BatchStrOutput, HealthCheckOutput, control outputs
rpc_ipc_name Engine DEALER ⇄ Scheduler rank-0 DEALER RpcReqInput / RpcReqOutput
metrics_ipc_name Scheduler PUSH → metrics consumer scheduler stats
nccl_port not ZMQ — torch.distributed / NCCL rendezvous
Design note The wire format is pickle by default: sock_send uses socket.send_pyobj(...) because SGLANG_USE_PICKLE_IPC defaults to True (environ.py). A msgspec/msgpack tagged-union path exists for every BaseReq/BaseBatchReq struct and can be enabled by turning that env off. 
def init_ipc_channels(self, port_args: PortArgs):
    context = zmq.asyncio.Context(2)
    self.recv_from_detokenizer = get_zmq_socket(
        context, zmq.PULL, port_args.tokenizer_ipc_name, True
    )
    if self.server_args.tokenizer_worker_num == 1:
        self.send_to_scheduler = get_zmq_socket(
            context, zmq.PUSH, port_args.scheduler_input_ipc_name, True
        )
        self.tokenizer_ipc_name = None
    else:
        # Use tokenizer_worker_ipc_name in multi-tokenizer mode
        self.send_to_scheduler = get_zmq_socket(
            context, zmq.PUSH, port_args.tokenizer_worker_ipc_name, False
        )

The three event loops

Each role runs one tight loop. Reading these three functions side by side is the fastest way to understand SGLang's runtime: 

@DynamicGradMode()
def event_loop_normal(self):
    """A normal scheduler loop."""
    while True:
        if self.gracefully_exit:
            break
        recv_reqs = self.request_receiver.recv_requests()
        self.process_input_requests(recv_reqs)
        if self._engine_paused:
            continue
        plan = self.get_next_batch_to_run(
            running_batch=self.running_batch, last_batch=self.last_batch
        )
        self.running_batch = plan.running_batch
        batch = plan.batch_to_run
        if batch:
            result = self.run_batch(batch)
            self.process_batch_result(batch, result)
        else:
            self.on_idle()
        self.last_batch = batch

def event_loop(self):
    """The event loop that handles requests"""
    while True:
        with self.soft_watchdog.disable():
            recv_obj = sock_recv(self.recv_from_scheduler)
        output = self._request_dispatcher(recv_obj)
        if output is not None:
            sock_send(self.send_to_tokenizer, output)
        self.soft_watchdog.feed()

async def handle_loop(self):
    """The event loop that handles requests"""
    while True:
        with self.soft_watchdog.disable():
            recv_obj = await async_sock_recv(self.recv_from_detokenizer)
        if isinstance(
            recv_obj,
            (BatchStrOutput, BatchEmbeddingOutput, BatchTokenIDOutput),
        ):
            await self._handle_batch_output(recv_obj)
        else:
            self._result_dispatcher(recv_obj)
        self.last_receive_tstamp = real_time()
        self.soft_watchdog.feed()
Why split detokenization into its own process? Incremental detokenization is pure CPU work (and must handle multi-byte UTF-8 characters that arrive split across steps — the detokenizer holds back text ending in a partial "�" until the character completes). Moving it out of the scheduler process keeps the GPU loop free of per-token string work, and moving it out of the main process keeps the asyncio HTTP loop responsive.

With dp_size > 1 the main process spawns a single DataParallelController subprocess, which spawns all dp_size × tp_size × pp_size schedulers itself and load-balances requests (data_parallel_controller.py). Each replica gets its own scheduler_input_ipc_name, but all replicas share one detokenizer and one tokenizer return path.
FlagEffect on topology
--tp-size NN scheduler processes per DP replica per PP stage; NCCL TP group across them.
--pp-size KMultiplies scheduler count; PP ranks > 0 receive requests via point_to_point_pyobj from the previous stage, not ZMQ.
--dp-size MActivates the DataParallelController; M independent replicas (each a full TP×PP world).
--enable-dp-attentionDP nested inside the TP group (see chapter 07); all ZMQ switches from ipc:// to TCP.
--nnodes / --node-rankNodes with node_rank ≥ 1 run schedulers only — no TokenizerManager, no detokenizer, just a dummy health-check server.
--tokenizer-worker-num Kuvicorn forks K HTTP workers, each with a private TokenizerWorker; a MultiTokenizerRouter fans traffic in/out.
--skip-tokenizer-initClient sends/receives token IDs; scheduler pushes BatchTokenIDOutput straight back, bypassing the detokenizer.
--load-balance-methodDPC policy: round_robin, total_requests, total_tokens (shared-memory load snapshots), follow_bootstrap_room (PD disaggregation).

1.6Notable facts & gotchas

  • The "model worker" is not a process. TpModelWorker / ModelRunner live inside each scheduler subprocess. The only GPU-facing processes are the schedulers.
  • Bind/connect direction is unusual: the TokenizerManager binds both its PUSH (to scheduler) and PULL (from detokenizer) sockets; schedulers and the detokenizer connect to it. Exception: the detokenizer binds its own PULL.
  • Crash propagation is via signals: a scheduler hitting an exception sends SIGQUIT to the parent process; a SubprocessWatchdog in the parent watches all children.
  • Health checks skip the queue: process_input_requests short-circuits health-check requests and replies with a bare HealthCheckOutput directly to the tokenizer socket when the engine is busy.
  • Sessions are scheduler-side state: /open_session creates a per-session tree of SessionReqNodes inside the scheduler (session/session_controller.py), letting multi-turn requests branch and continue server-side.
  • An embedded Rust server can replace three Python components: with SGLANG_RUST_SERVER=1, the rank-0 scheduler embeds a Rust API server owning HTTP + tokenization + detokenization, draining an in-process ring buffer instead of ZMQ.
  • The DP controller keeps immortal threads: each DP replica launcher thread sleeps ~30 days in a loop forever, because exiting it would trigger kill_itself_when_parent_died in the child schedulers.
